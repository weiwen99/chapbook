#+TITLE: Spike: orgize 渲染质量对比报告
#+DATE: 2026-08-05

* 结论

orgize 在可靠性上**碾压 pandoc**（语料 213 文件中 pandoc 失败/超时 78 个占 37%，
orgize 213/213 全部成功，且毫秒级无子进程），结构保真度也高于 pandoc 与 emacs
（后两者都会丢 4 级标题，orgize 与源码一致）。

**但 orgize 有两个可见能力缺失**：不输出语法高亮 token、不导出 TOC。是否切换取决于
这两项能否接受（或愿意叠加 syntect / 自建 TOC）。

* 方法

- 语料：=0x2/profile-agents/docs= 全部 213 个 .org（8.1MB）
- orgize 0.9.0（crates.io 稳定版；0.10 仅 alpha）；pandoc 3.9.0.2（10s 超时，语料中存在让
  pandoc 病态 hang 的文件）
- 保真度代理指标：对输出 HTML 做结构计数（h1–h6 / table / pre / code 数量），三方互比 +
  与源码标题数对照；emacs batch 抽查 3 个 pandoc 失败文件作参照

* 数据

** 成功率

| 渲染器 | 成功 | 失败 | 失败原因 |
|--------+------+------+----------|
| pandoc | 135/213 (63%) | 78 | 解析错误 / 病态 hang（如 =plan-11-mcp.org= 40KB 跑 3 分钟+）|
| orgize | 213/213 (100%) | 0 | 无 panic、无错误 |
| emacs  | 抽查 3/3 | 0 | 仅抽查，~3s/文件太慢 |

** 结构保真（双方都成功的 135 个文件）

| 指标 | 数值 |
|------+------|
| h/tbl/pre 三项计数与 pandoc 完全一致 | 130/135 (96%) |
| 有分叉 | 5/135，全部是 pandoc 丢标题（orgize 更多，且 orgize 是对的）|

** 分叉与标题保真（plan-56 实测）

| 渲染器 | h2 | h3 | h4 | 合计 | 对照源码 |
|--------+----+----+----+------+----------|
| 源码真值 | 8 | 4 | 17 | 29 | — |
| orgize | ~ | ~ | ~ | 30 | ≈ 29（±1 边界噪音）|
| emacs  | 2 | 8 | 4 | 14 | **丢 13 个 h4** |
| pandoc | ~ | ~ | 0 | 13 | **丢全部 17 个 h4** |

即：你文档里 =****= 4 级小节（架构、被拦截的 IP 类等）在 pandoc/emacs 渲染里**直接消失**，
orgize 全部保留。orgize 是三者中最忠实的。

** code 计数差异（无内容丢失）

orgize 的 src 块输出 =<pre class="src src-scala">= 且**不含内嵌 =<code>=**（pandoc 有），
故 code 计数 pandoc 多 ~70/文件——纯输出格式差异。

** CJK 边界 verbatim（与渲染器无关）

= =None=（=Tool.scala:75-100=）= 这类「verbatim 紧贴全角标点」的构造，orgize 与
pandoc/emacs 行为完全一致（同样错配成一个大 span）——org 语义边界规则使然，属于文档
内容问题，不构成选型差异。

* orgize 输出结构与现有 CSS 适配

| 输出结构 | 与 chapbook-doc.css 兼容性 |
|----------+---------------------------|
| =<main><section>= 包裹、h1–h6 | ✓ 无冲突 |
| =<table><thead><tbody>= | ✓ 现有表格样式直接生效 |
| =<pre class="src src-scala">= | ✓ 已有 =pre.src= 选择器 |
| =<i>= 代替 pandoc 的 =<em>= | ✗ 需补 =i= 样式（1 行）|
| 无 =<nav id="TOC">= | 宽屏 =:has(#TOC)= 守卫已兼容（无 TOC 即无侧栏）|
| **无语法高亮 token**（代码块纯文本） | 可见能力缺失，见下 |
| **无 TOC 导出** | 可见能力缺失，见下 |

* 决策建议

| 选项 | 收益 | 代价 |
|------+------+------|
| A. 切 orgize（主）| 100% 可靠、毫秒级、结构更忠实、零子进程；emacs 兜底链可删 | 代码块失去语法高亮；TOC 侧栏消失（可自建轻量 TOC，~0.5 天）|
| B. 维持现状（pandoc → emacs → 原文）| 保留高亮 + TOC | 37% 文档走 ~3s 的 emacs 兜底；4 级标题在 pandoc/emacs 下结构性丢失 |
| C. orgize + syntect 高亮叠加 | 兼得可靠性与高亮 | syntect 需嵌入语言语法集（二进制 +2–5MB）+ 调色板重做；工作量 +1–2 天 |

* 我的建议

先做 **A**（0.5–1 天）：org 路径切 orgize，接受代码块无高亮（org 文档里代码块不是主视觉
元素，且内容完整），自建轻量 TOC 恢复侧栏；同时删掉 emacs 兜底与 org 的 pandoc 路径。
若后续想要代码块高亮，再评估 C（syntect 也顺带服务 .md 与代码文件路径，届时 pandoc 可
整体退出运行时依赖）。
